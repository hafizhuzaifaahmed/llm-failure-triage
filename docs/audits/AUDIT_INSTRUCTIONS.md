> **Superseded for the label audit (D-82, 2026-11-03).** Use the kit in `docs/audits/kit/`: blind packets per rater (`packets_rater_A.pdf`, `packets_rater_B.pdf`, each rater's own seeded order), the rubric (`LABEL_AUDIT_RUBRIC.md`, PF / TF / AMB with worked examples), 10 calibration items (`calibration_rater_X.csv`, key in `CALIBRATION_KEY.md`, opened only after calibration) and the audit sheet (`label_audit_rater_X.csv`). Score with `python scripts/analysis/label_audit.py`. The older `label_audit_rater_A/B.csv` sheets below (ATTRIBUTABLE / NOT_ATTRIBUTABLE / UNSURE) are not to be used: their fix patches are shown in the source's fixed → buggy direction, which the kit inverts to buggy → fixed.

Two audits are required by the Phase 2 methodology. Each author receives an identical sheet (rows already in
a random order) and fills it **without conferring**. Disagreements are discussed only after both sheets are
complete and scored. Sheets are generated by `scripts/make_audit_sheets.py`; scoring by
`scripts/score_audits.py`. **Status: sheets are not yet generated** — they need the real development-split
instances (label audit) and the real inferred specifications (spec audit), which do not exist until the
approved pilot has run.

## 1. Label audit — 100 instances (50 PF, 50 TF), development split

Files: `docs/audits/label_audit_rater_A.csv`, `label_audit_rater_B.csv`.

Each row shows the generated test, the failure observed on the **buggy** version, and the fix patch. The
automatic label and the outcome on the fixed version are deliberately hidden.

Question: *Is the failure on the buggy version caused by the code that the fix changes?*

| `decision` value | Meaning |
|---|---|
| `ATTRIBUTABLE_TO_FAULT` | the test exercises the faulty behaviour and fails because of it (the test is right) |
| `NOT_ATTRIBUTABLE` | the test would fail regardless of the fault: wrong expectation, invalid set-up, API misuse |
| `UNSURE` | cannot decide from the evidence; explain in `notes` |

Reported: agreement of each rater with the automatic label (UNSURE excluded and counted), Cohen's κ
between raters. A systematic disagreement leads to a revision of the labelling rule **before** any test-split
run (Phase 2, Section 3.4).

## 2. Specification leakage audit — 60 inferred specifications (S2)

Files: `docs/audits/spec_audit_rater_A.csv`, `spec_audit_rater_B.csv`. Stratified by project.

Each row shows the focal signature, the S2 specification and the fix patch.

| `classification` value | Meaning |
|---|---|
| `STATES_FIXED` | the specification states the behaviour the fix introduces |
| `STATES_BUGGY` | the specification states the buggy behaviour |
| `SILENT` | the specification says nothing that distinguishes buggy from fixed behaviour |

Reported: the proportion of each class per rater and Cohen's κ, alongside any S2 effect (Phase 2, Section 3.6.1).
